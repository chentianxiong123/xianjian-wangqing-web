### 2.1 渲染算法（★这是「角色渲染是碎的」的真正原因）

出处 `y.java` 的 `a(Graphics, Image[], ...)`。

一个 `y`（图层组）= 一组 `{clipIndex, x, y, flags}`。
每条记录引用裁剪表里的一块矩形，再按 `flags` 做变换，
最后按图层组顺序**从前往后绘制（后画的在上层，y.java:86）**，
目标点就是 `base+offset`（y.java:94-95，**不做任何居中**）。

`flags` → `drawRegion` transform（`ag.java` 10 参重载，字节码 javap 逐项核对）：

| flags | transform 编号 | J2ME 语义（MIDP 2.0 Sprite 常量） | 目标尺寸 |
|---|---|---|---|
| 0 | 0 | NONE | w,h |
| 1 / 10 | 2 | MIRROR（水平镜像） | w,h |
| 2 / 9 | 1 | MIRROR_ROT180（= 垂直翻转） | w,h |
| 3 / 8 | 3 | ROT180 | w,h |
| 4 | 5 | ROT90（顺时针 90°） | h,w |
| 16 | 6 | ROT270 | h,w |
| 5 / 18 | 4 | MIRROR_ROT270（= 转置） | h,w |
| 6 / 17 | 7 | MIRROR_ROT90 | h,w |
| 7 / 11-15 | 抛异常 | 非法 | — |

★ 注意 J2ME 常量**不是** 0-7 顺序（`ROT90=5, ROT180=3, MIRROR=2, MIRROR_ROT180=1…`），
之前按顺序理解导致朝右人物被画成倒立。判定方法（三重锁定）：
① y.java 裁剪表的源矩形调整数学（左/右/上/下剔除分别吃哪边）；
② swap 规则（`flags&4|&0x10`）恰好覆盖全部转置类变换；
③ 数据实证（站立右 = 站立左各部件的水平镜像，旋转 180° 则是倒立）。

**关键**：`nArray4[3]` 是裁剪表里的 **w**，`nArray4[4]` 是 **h**。当 `flags & 4`（或 `& 0x10`）时，绘制尺寸要交换 w/h。前人把 c_table 当成「5×uint16、10 字节」解析，**导致整体错位**，所以角色渲染成了碎纹理。

### ★★ 旧实现为什么错、错在哪

旧实现把文本按 `[\x00-\x1f]` 切分。**int16 长度字段的高位字节通常是 `0x00`，被当成了分隔符**，
于是每个条目前面都多出一个垃圾字节：

| 正确 | 旧实现看到 |
|---|---|
| `对话区域 = {...}` | `Z对话区域 = {...}` |
| `5最大生命 = ...`（键名本就以 5 开头） | `5最大生命` ✓ 碰巧对 |
| `木剑#武器#1#...` | `R木剑#武器#1#...` |
| `对话文件 = talk_21.str` | 键名被污染 |

length < 256 时高字节恰为 `0x00`，**看起来完全像分隔符，极具欺骗性**；
length ≥ 256 时（如 384 = `01 80`）高位是 `0x01`，才暴露出来。
`config_game.str` 的「帮助 = ...」条目长 384 字节，是暴露点。

结构是暴力搜索 + 逐字节核对得出的：先假设「magic + int16 版本 + 定长头」并用已知
文本（`扭曲延迟 = 500` 等）的字节偏移反推，再全量回归验证 101 个文件。

   `(1+20)/20 = 1`。后果：**所有怪物的技能公式里 `slv` 恒为 1**，`仙术速度` 恒为 10。
   真实等级只通过 `bm` 的变量 **`lv`** 参与生命/速度/经验/金钱求值。
2. **怪物防御恒为 0**：`g.java:31  this.m(0)`，神与气也恒为 0。
3. **增益取施法者的攻防**：`addatk` 用施法者 `K` 而非目标（`ax.java:1026`）。
4. **`addspeed` 固定 +1**：与技能等级无关（`ax.java:1045`）。
5. **阵亡扣好感度不扣经验**，且精强制置 1（`f.java:1069`）。
6. `config_skill.str` 第 0 行不是数据行，被 `d.java:249` 硬编码成变身槽
   `af(0,"none","none","name","攻击","否","0","0","否","0","0","atk",null)`，
   其技能类型落到 `af.java:24` 的 else → **7 = 变身**。

## 7.3 MID 的两处原始数据异常

`ssm.mid` 在最后一个 `MTrk` 之后残留 **3 字节 `0d 0d 0a`**（偏移 5977），
`syg.mid` 残留 **1 字节 `0d`**（偏移 5761）。
这是原始 jar 里就有的数据，J2ME 播放器会忽略，故 `parse_smf` 以 `anomalies` 记录而非报错。
`byte_exact` 对 MID 的判定是「所有 chunk 长度累加 == 文件长度 − 残留字节数」。

## 7.4 ★ 原版数据里的 4 类拼写错误（原引擎会静默忽略，复刻必须照做）

地图脚本是作者手写的，存在 4 类拼写错误。共同后果是：

### 字段语义（f.java:346 d(int)）
- **ID范围**：`9` = 单个 id；`1-2-5` = 三个候选 id 随机取
- **怪物种类**：`2` = 双种怪（按 f.java:350 的表拆分数量）；其它 = 单种
- **等级范围**：`60` = 固定；`0-20` = 区间（怪物等级 = 主角等级 ±1 再夹区间）；
  `#事件ID?成立段:不成立段` = 条件选段
- **战斗背景 / BGM**：战斗画面 ANT 与音乐

### 怪物属性来自 `fight_<id>.str`，两种存放方式
| 产物字段 | 内容 | 例子 |
|---|---|---|
| `scalars` | 字面量 | fight_9 最小生命 = `"50000"` |
| `formulas` | 含 `lv`/`slv` 的表达式 | fight_2 最小生命 = `((100+26*lv)*(2+lv/5+lv/10-lv/20))*3/2` |

★ 取值时**两处都要查**，只查 `scalars` 会让全部公式型怪物属性变成 0。

产物把 `普通技能` / `仙术技能` 整行按 `#` 拍平成一个 `cols` 列表

### ★ H2.str（之前误记为空，已纠正）
`game.fight(key, t1, t2, t3)` 的第 2 参数是 `H2.str` 的**条目索引**

## 8. 质量标准（本项目强制）

1. **溯源**：每条数据带 `source: {file, offset}` 或 `src: {class, line}`，能回溯原始字节/源码
2. **穷尽校验**：每个解析器 `assert` 字节**正好耗尽**，有残留立即报错。
   这是我能断言「ANT 75/75、MAP 69/69、BIN 18/18 字节级正确」的唯一依据。
3. **覆盖率报告**：`90-校验.py` 生成 `manifest.json`，明确列出未解部分，**不允许静默漏**
4. **不确定就标注**：不许猜充数。挖不出来的单列「未确认」。
5. **产物可回溯校验**：指令表的每条 `src.line` 必须真的指向源码里含该指令名的行；
   表达式引擎语义必须有正例 + 反例用例；覆盖率数字由产物自动判定，**禁止手填**。
6. **管线可从零重建**：删掉全部产物后依次跑
   `20 → 25 → 30 → 40 → 50 → 90` 必须得到同样的结果且 0 错 0 警。
