## 1. 压缩层

**所有 `.ant/.map/.str` 都是 gzip 包裹的 raw DEFLATE 流。**
- `x.java` 负责剥 gzip 头，然后交给 `ai`（手写 inflate）
- 所以：**先 `gzip.decompress()`，再按下面的裸格式解析**
- 例外：`.bin` 文件**有的压有的不压**（判断前 2 字节 `1f 8b`）
- 例外：`.pix` 条目的**负载本身还是 gzip 的**，需再解一层

### 2.1 渲染算法（★这是「角色渲染是碎的」的真正原因）

出处 `y.java` 的 `a(Graphics, Image[], ...)`。

一个 `y`（图层组）= 一组 `{clipIndex, x, y, flags}`。
每条记录引用裁剪表里的一块矩形，再按 `flags` 做**翻转/镜像**，最后按图层组顺序**从后往前叠加绘制**。

`flags` 位定义（从 `y.java` 的 `switch` 和 `(flags & 4) != 0 || (flags & 0x10) != 0` 判断反编译得出）：

| 值 | 含义 |
|---|---|
| 0 | 原样 |
| 1 / 10 | 垂直镜像 |
| 2 / 9 | 水平镜像 |
| 4 | 宽高对调（90°） |
| 3 / 8 | 双向镜像（180°） |
| 16 | 对角镜像 |
| 5 / 18 | 顺时针90° |
| 6 / 17 | 逆时针90° |

**关键**：`nArray4[3]` 是裁剪表里的 **w**，`nArray4[4]` 是 **h**。当 `flags & 4`（或 `& 0x10`）时，绘制尺寸要交换 w/h。前人把 c_table 当成「5×uint16、10 字节」解析，**导致整体错位**，所以角色渲染成了碎纹理。

## 3. MAP 场景格式 `88MAP`

出处：`w.java`。**已验证 69/69 字节精确耗尽。**

```
'88' 'M' 'A' 'P'          4B
0x05                     1B   版本（必须 ==5）
bool                     1B   保留
int32                    4B   资源标记（实测 -1 / -16777236 等，未知含义）
int16 tileW, tileH       4B   瓦片像素尺寸（全部 16×16）
UTF   script             --   ★★ 整段地图脚本（事件/传送/NPC 定义都在这里）

int16 cols, rows         4B   瓦片列数 / 行数
layerCount × {
   UTF  name             --   "地砖" / "元素" / "遮挡"
   bool hasTiles

   int16 nObj
   nObj × { int16 animIndex; int32 x; int32 y; bool → UTF script }

```

- `animIndex` 是**元素 ANT（地图自己的，不是 mishi）命名状态数组的下标**
- 图层顺序固定：`[0]=地砖` `[1]=元素`(带区域/触发器) `[2]=遮挡`
- 世界尺寸 = `cols*tileW` × `rows*tileH`

### 3.1 地图用哪个元素 ANT？

所以地图→ANT 是**多对多**的（同一张地图可能从不同入口进来，ANT 不同）。

## 4. BIN 资源包 `88BIN`

出处：`x.java`。**已验证 18/18 字节精确耗尽。**

```
'88' 'B' 'I' 'N'          4B
0x09                     1B   版本
int16 count
count × { UTF name; int32 len; byte[len] data }
```

**条目名决定内容：**
- `*.png` → 直接就是 PNG 字节
- `*.pix` → PIX 格式（见下），且**负载还是 gzip 的**
- `#其他.bin:下标` → **跨包引用**，本条目无数据（len=0），需去另一个 BIN 取

`x.java` 的解析循环：
```java
object = prefix + name;
object = x.a(stream(object), idx);
if (object.a.charAt(0) != '#') break;     // 不以 # 开头就结束
object = split(object.a.substring(1), ":");
idx = Integer.parseInt(object[1]);
object = object[0];                        // 另一个 bin 名
```

⚠️ **前人的 `bin_index.js` 只数了 `.png` 个数，漏掉 `.pix` 和 `#引用`，导致所有 sheet 下标错位。**

## 5. STR 配置/脚本 `88STR`

**已验证 101/101 文件字节精确耗尽，1146 个条目全部对齐。**
本节曾长期是错的（前人用 `[\x00-\x1f]` 切分文本），2026-10-04 已修正。

```
'88' 'S' 'T' 'R'          4B   magic
uint8  version            1B   实测恒为 6
uint8  reserved           1B   实测恒为 0
uint8  entryCount         1B
entryCount × { uint16 BE length; byte[length] UTF-8 text }
```

### ★★ 旧实现为什么错、错在哪

旧实现把文本按 `[\x00-\x1f]` 切分。**int16 长度字段的高位字节通常是 `0x00`，被当成了分隔符**，
于是每个条目前面都多出一个垃圾字节：

| 正确 | 旧实现看到 |
|---|---|
| `对话区域 = {...}` | `Z对话区域 = {...}` |
| `5最大生命 = ...`（键名本就以 5 开头） | `5最大生命` ✓ 碰巧对 |
| `木剑#武器#1#...` | `R木剑#武器#1#...` |
| `对话文件 = talk_21.str` | 键名被污染 |

length < 256 时高字节恰为 `0x00`，**看起来完全像分隔符，极具欺骗性**；
length ≥ 256 时（如 384 = `01 80`）高位是 `0x01`，才暴露出来。
`config_game.str` 的「帮助 = ...」条目长 384 字节，是暴露点。

结构是暴力搜索 + 逐字节核对得出的：先假设「magic + int16 版本 + 定长头」并用已知
文本（`扭曲延迟 = 500` 等）的字节偏移反推，再全量回归验证 101 个文件。
